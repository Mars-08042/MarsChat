# ADR-0001 Service 层三元返回值与错误分级

- 状态：已被 [ADR-0005](0005-distributed-architecture.md) 替代（2026-11-18，旧代码已在重构中移除）；原状态为已采纳（追溯记录）
- 日期：2026-11-07 整理

## 背景

后端需要同时满足两点：前端能拿到可以直接展示给用户的提示；数据库、缓存等内部异常不能泄露给前端，只用于排查。

依据：`api/v1/controller.go` 的 `JsonBack`、各 service 方法签名，以及基线代码附带的一份业务约定说明（已删除，要点并入本文和旧版 `system.md` 的 5.1 节，见提交 `6624cea`）。

## 候选方案

无记录。

## 决策

1. Service 方法返回 `(message string, [data,] ret int)`，不向上返回 `error`。
2. `ret = 0` 成功；`ret = -2` 业务错误（如用户被禁用、实例无法创建）；`ret = -1` 系统错误。
3. Controller 统一调用 `JsonBack`，分别映射为响应体 `code` 200 / 400 / 500，HTTP 状态码始终为 200。
4. 系统错误时 `message` 固定为 `constants.SYSTEM_ERROR`，错误详情只通过 `zlog.Error` 写日志；业务错误同样用 `zlog.Error` 记录，便于排查。
5. 打开用户或群聊会话前，默认双方关系不是删除/被删除、退群/被踢出（群解散也视为被踢出），在此前提下再判断对方是否被禁用、自己是否被禁言，以决定能否打开以及打开后的状态。

## 原因

原始说明的表述是：message 是业务问题，返回给前端用于提示或调试；error 是系统问题，不应返回前端，由后端通过日志排查。

## 代价与风险

- HTTP 状态码不携带语义，网关、监控、浏览器开发者工具都无法按状态码区分失败请求，前端每次都必须检查 `code`。
- 请求体绑定失败（客户端错误）也返回 `code: 500`。
- Service 不返回 `error`，调用链上无法用 `errors.Is` 判断错误类型，也不便于单元测试断言。

## 适用条件

只要前端仍按响应体 `code` 判断结果就保持此约定。若改为标准 HTTP 状态码或引入 OpenAPI 规范，应新写 ADR 替代本条，并同步修改前端所有调用。
