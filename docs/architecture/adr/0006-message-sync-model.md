# ADR-0006 消息同步模型：读扩散、会话内 seq 与游标补拉

- 状态：已采纳（2026-11-18 开发者确认）
- 日期：2026-11-18
- 关联：[ADR-0005](0005-distributed-architecture.md)、[后端重构计划](../../plans/active/backend-refactor.md)

## 背景

旧基线中，发送状态由服务端回显决定（ADR-0003），消息没有序号、确认和补拉；离线消息只在打开会话时全量读取；同一用户重连会覆盖在线表，不支持多端。

新架构需要在多实例下同时满足：会话内有序、不丢不重、多端同步、断线补齐、未读与已读。

## 候选方案

| 方案 | 说明 | 代价 |
|---|---|---|
| A 写扩散 + 每用户 pts（teamgram 私聊和普通群的做法） | 每条消息为每个成员写一份副本，并分配该成员的递增序号；客户端只比对一个 pts 就知道是否遗漏 | 存储放大 N 倍，一条群消息要写 N 行 |
| B 读扩散 + 会话内 seq | 消息按会话只存一份，会话内递增 seq；每个成员只记录已读位置和同步游标 | 重连时要逐个会话比对 |
| C 只靠推送确认与重试 | 不引入序号，推送失败就重试 | 离线、乱序和多端都难以处理 |

## 决策

采用方案 B：

1. 消息按会话只存一份。发送时在事务内用会话行锁分配 seq，消息与 Outbox 事件在同一事务中写入。
2. 客户端为每条消息生成 `client_msg_id`，用（发送者，`client_msg_id`）唯一约束保证幂等，重复请求返回首次的结果。
3. 写库成功即返回确认，带服务端消息 ID 和 seq；客户端超时未收到确认就重发。
4. 实时推送尽力而为，失败不重试；可靠性由 seq 补拉保证。推送给发送者的其他设备时，排除发起设备。
5. 重连时拉取会话列表（含各会话的最大 seq 和本人游标），对有缺口的会话按 seq 补拉。补拉结果分三种：完整补齐、分批补齐、缺口过大要求客户端重载（参考 teamgram 的 getDifference）。
6. 未读数 = 会话最大 seq − 本人已读位置。已读位置变化作为事件推给本人的其他设备；单聊用对方的已读位置做已读回执；群聊不做逐人已读列表。
7. 撤回、编辑作为会话事件，进入同一个 seq 序列。

## 原因

- 群规模中小（不支持超大群），消息只存一份最简单，发送延迟与群人数无关。
- 会话内有序足以满足 IM 体验，不需要全局有序。
- 推送与可靠性解耦：推送路径保持简单，可靠性集中在数据库写入和补拉上。

## 代价与风险

- 用户会话很多时，重连比对的成本较高（teamgram 只需比对一个 pts）。
- 热点群的 seq 行锁可能成为写入瓶颈。
- 好友申请、被拉入群等用户级事件不在会话序列中，重连时靠刷新列表兜底。
- 群聊不提供逐人已读。

## 适用条件（何时需要重新评估）

- 单个用户的会话数很多，重连比对成为瓶颈：引入每用户更新日志（只写扩散索引，不复制消息）。
- 出现热点大群：seq 分配改为 Redis 原子递增加持久化，或单独设计大群模型。
